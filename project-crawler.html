Concurrent web crawler

Start from a homepage and map every URL reachable by following links. Written in Go as an exercise during my internship at KYND.

  • Go
  • Concurrency
  • 2023

What it does

Given a starting URL, the crawler fetches the page, extracts every link, keeps the ones on the same site, and repeats until it has run out of new pages to visit. What comes out is a sorted list of every URL discoverable from that starting point.

I ran it against KYND’s public site and against monzo.com as a larger target — the monzo run found 5,322 URLs.

Doing it concurrently

Crawling is almost entirely spent waiting on the network, so fetching one page at a time leaves the program idle most of the time. Instead it runs many fetches at once — up to 128 goroutines in flight, coordinated with a WaitGroup and a counter guarded by a mutex.

That is where the real problem starts. Every worker is discovering links at the same time, and they all need the same three pieces of state: the queue of URLs still to visit, the set of URLs already visited, and the set of domains allowed. Those are sync.Maps, so many goroutines can read and write them without corrupting each other — and, just as importantly, without two workers deciding to fetch the same page.

Keeping the crawl cheap

A crawler that follows every link it sees will happily wander off into the rest of the internet and never finish, so several filters run before a URL is ever fetched:

  • Same site only, treating www. and the bare domain as one.
  • HTTPS links only.
  • Skips images, PDFs and audio by file extension — no point spending a request and an HTML parse on a file with no links in it.
  • Checks both the queue and the visited set, so nothing is queued twice.

Checking it was actually right

A crawler that silently misses pages still looks like it works, so I benchmarked mine against gocolly/colly, an established Go crawling library, as a reference implementation.

Both were run over the same site and the results diffed in both directions: which URLs colly found that mine had missed, and which mine found that colly had not. Both runs were timed, so correctness and speed could be compared together.

Alongside that, 21 unit tests cover the parts worth testing in isolation — domain extraction, link parsing, the relevance and file-type filters, and the visited set.
